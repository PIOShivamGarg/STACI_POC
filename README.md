# Staci 8.2 POC: Forecasting and Inventory-Shortfall Early Warning

Proof of concept for two forecasts a 3PL warehouse needs:

1. **Order Volume:** how many orders each client / warehouse / sales channel will receive per week, 1–13 weeks ahead (staff and capacity planning).
2. **Shortfall Risk:** which items are likely to run out before replenishment can arrive, with a projected stockout date, a RED / AMBER / GREEN / BLUE state, a reason and a suggested reorder quantity.

Both are built from one weekly **SKU demand forecast** with two figures per item and week:
- **P50:** the likely figure.
- **P90:** a safer, higher figure, which actual demand should stay under about 90% of the time.

Numbers come from forecasting models and plain arithmetic, never from a language model. Every output row carries `created_at` and `method_version`, so you can always trace which run and which model produced it.

> All data is **synthetic** (fictional, generated by `generate_data.py`), shaped like a real warehouse extract.

## Quick start

```powershell
python -m venv venv
.\venv\Scripts\activate
pip install -r requirements.txt

python generate_data.py          # creates data/ (synthetic, fixed seed)
copy .env.example .env           # then set FORECAST_MODEL in .env

python forecast.py               # SKU demand forecast + backtest
python risk.py                   # order volume + shortfall alerts
python build_xlsx.py             # optional Excel workbook
python compare_models.py         # side-by-side table of every model run so far
```

To run another model, change `FORECAST_MODEL` in `.env` (or set it in the shell, which takes priority) and run the scripts again. Each model writes to its own folder, so runs don't overwrite each other.

## Models

| `FORECAST_MODEL` | Model | How it works |
|---|---|---|
| `lgbm` | LightGBM | One model for all SKUs, trained on lag, rolling-average, seasonal and event features. P50 uses a Tweedie objective, P90 a 0.9 quantile objective. |
| `xgboost` | XGBoost | Same features and settings as LightGBM, for comparison. |
| `chronos` | Chronos-2 (Amazon) | Pre-trained time-series foundation model, used without training on our data. Forecasts the 0.5 / 0.9 quantiles from each SKU's history, with event uplift as an input. Downloads about 0.5 GB of weights on first run, then works offline on CPU. |
| `stats` | MSTL + ETS / TSB | Classic statistical baseline, one model per SKU. Regular sellers use MSTL + AutoETS (yearly pattern plus smoothed level and trend); slow movers use TSB (intermittent demand). |

All four are free and open source. Adding a model means one file in `models/` and one line in `config.py`.

## How it works

```
data/ ──► forecast.py ──► sku_forecast.csv ──► risk.py ──► order_volume_forecast.csv
                                                     └───► inventory_risk.csv
```

- **`forecast.py`**
  - Sums daily demand into weeks.
  - Forecasts 13 weeks ahead with the chosen model.
  - **Backtests** on two past windows, the last 13 weeks and last year's peak season. For each window it pretends to be at an earlier date, forecasts, and compares the forecast with what actually happened.
- **`risk.py`**
  - **Order volume:** converts units to orders using each SKU's recent orders-per-unit ratio, then sums by client, warehouse, channel and week.
  - **Shortfall risk:** projects each SKU's stock day by day as `available − forecast demand + inbound ASNs`. The first day the balance goes below zero is the stockout date. States:
    - **RED:** runs out before stock can arrive.
    - **AMBER:** reorder now.
    - **GREEN:** covered.
    - **BLUE:** excess, more than 90 days of cover.
  - Reorder quantities are sized on P90.

## Outputs

`outputs/<model>/`:

| File | Contents |
|---|---|
| `sku_forecast.csv` | Weekly P50 / P90 per SKU for the next 13 weeks |
| `order_volume_forecast.csv` | Weekly units and orders (P50 / P90) per client / warehouse / channel |
| `inventory_risk.csv` | One row per SKU: available stock, days of cover, stockout dates, risk state, reason, reorder qty |
| `backtest_accuracy.csv` | Per-SKU forecast vs actual on both backtest windows |
| `feature_importance.csv` | Which features drive the model (LightGBM / XGBoost only) |
| `summary.json` | Backtest scores for SKU demand, Order Volume and Shortfall Risk |
| `risk_summary.json` | Count of SKUs in each risk state |

`outputs/model_comparison.csv` puts every model side by side, per deliverable, with the naive benchmark.

## Measures

- **WAPE:** total absolute error ÷ total actual. Lower is better.
- **P90 coverage:** the share of cases where actual stayed at or below P90. It should be close to 90%.
- **Naive benchmark:** "the last 4 weeks' average continues". Every model must beat it.
- **Shortfall Risk score:** this is a proxy. It compares forecast and actual demand over each SKU's lead time. A true alert backtest (did flagged items really run short?) needs historical stock snapshots, which the synthetic data does not include.

## Results on the synthetic data

WAPE, normal weeks / peak season (lower is better):

| | LightGBM | XGBoost | Chronos-2 | Stats | Naive |
|---|---|---|---|---|---|
| Order Volume | **13.4%** / 17.4% | 13.9% / **17.2%** | 13.5% / 19.8% | 15.3% / 18.9% | 15.2% / 32.2% |
| Shortfall Risk | 14.2% / 18.0% | 14.2% / 17.3% | **13.5%** / 16.0% | 18.5% / **15.2%** | 16.5% / 21.3% |

- **No single winner.**
  - LightGBM and XGBoost lead on Order Volume.
  - Chronos-2 is the most consistent on Shortfall Risk.
  - The statistical baseline is strong in peak season but doesn't beat naive in normal weeks.
- **All models flag the same 12 RED items.**
- **Known weak spots, shared by every model:**
  - P90 coverage at SKU level in peak season is about 72–77%, below the 90% target.
  - Slow-moving SKUs have high weekly error.
